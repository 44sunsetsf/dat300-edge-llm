# 研究结果：llama.cpp 在树莓派上做分布式推理，瓶颈在哪里、怎么优化

模型 Llama-3.2-3B-Instruct Q4_0（1.78 GiB）。llama.cpp 用我们的 fork `44sunsetsf/llama.cpp`，`dat300` 分支。
- 原版 = 上游 commit bd4eeaa；
- 改进版 = a8cd154，也就是 bd4eeaa 加上我们的补丁：
  - 846e5d9：N 节点之间直接 allreduce；
  - c1212b5：计时日志；
  - a8cd154：小数据的同步直接在内存里相加、可选 all-gather 算法、修复 8 台时初始化可能卡死的问题。

除非另外说明，Pi 上的测量条件都是：2 台 Pi 400（cassian 当 head，rex 当 worker），网线接宿舍路由器，两台之间 ping 0.70 ms；`llama-bench -p 32 -n 30 -r 2`。

## 一句话结论

1. **单台 Pi 的 decode 受内存带宽限制。** 每生成一个 token 要把 1.78 GB 权重读一遍，1.85 tok/s 对应约 3.3 GB/s，这已经接近 Pi 4/400 内存带宽的上限。TP 之所以能提速，是因为每台机器只需要读一半权重。
2. **网络带宽不是瓶颈。** TP 每个 token 只传约 0.7 MB，按 2.9 tok/s 算大约 2 MB/s，千兆网有约 117 MB/s。
3. **真正的瓶颈是"同步次数 × 每次同步的延迟"。** TP 每个 token 要做 56 次 allreduce（28 层，每层 2 次），每次的数据量很小（12 KB），但都要等对方。节点越多，原版 llama.cpp 越糟：
   - 原版只有在恰好 2 个节点时，才让节点之间直接交换数据；
   - 3 个及以上节点时，所有数据都要先回到 head 再转发；
   - 在 Mac 上模拟 8 个节点时，每个 token 有 **4164 次串行的网络延迟**，比一台 Pi 自己跑还慢。
4. **PP 每个 token 只有几次串行网络往返，对延迟几乎不敏感。** 但各段只能轮流计算，所以单个请求的 decode **永远不会比单台 Pi 快**（实测 1.81 tok/s，单机是 1.85）。PP 的价值在于能装下单台装不下的大模型，以及同时处理多个请求时的吞吐，不在于单个请求的速度。

### 人为加延迟：每 token 有几次串行网络延迟（只在 rex 的出口加 2 ms）

### 每个 token 的时间都花在哪里（计时日志，2 台 TP，改进版，3 线程）

用改进版 rpc-server 的计时日志（[`计时日志.md`](计时日志.md)）拆分平均每个 decode token 的时间，单位 ms：

| 节点 | 总时间 | 计算 | 同步（其中网络） | 收发数据 | 空等主控 |
|---|---|---|---|---|---|
| cassian（主控） | 353.8 | 315.9 | 26.0（21.7） | 1.4 | 6.8 |
| rex | 353.1 | 312.8 | 28.6（24.2） | 0.9 | 7.9 |

结论：
- **2 台时计算占约 90%，同步只占 7–8%。** 所以在 2 台、并且用了 `-t 3` 以后，瓶颈已经回到计算本身（每台读一半权重的内存带宽）。
- 台数增加后，计算会按 1/N 下降，同步次数不变（每个 token 56 次）、每次的轮数按 log2 N 增加。所以同步会成为主要部分，这正是 8 台实测要验证的。
- 原始日志在 `logs/trace/example_tp_2n_opt_t3/`。

### 为什么 `-t 3` 能快 21–26%

主要原因是**内存带宽**：decode 每个 token 都要把权重从内存读一遍，3 个线程已经把内存带宽用满，第 4 个线程只会增加争抢。单机也是 3 线程更快（1.93 vs 1.85 tok/s，见下面的补充实验）。

次要原因：主控上 llama-bench 的 RPC 调度线程是**忙等**的（`busy_spin_acquire`），会占着一个核。

代价：prefill 是纯计算，少一个线程就慢约 22%（7.6 → 5.9 tok/s）。
- 看重 decode（逐字输出的速度）：用 `-t 3`；
- 看重首 token 时间（长 prompt）：用 `-t 4`。

### 补充实验（2026-10-14，cassian / rex）

| 实验 | 结果 | 说明什么 |
|---|---|---|
| 单机 decode，`-t 3` vs `-t 4` | **1.93** vs 1.85 tok/s | 单机也是 3 线程更快：decode 完全被内存带宽卡住，第 4 个线程只会抢带宽。`-t 3` 更快不只是因为主控在忙等 |
| 单机 prefill（pp32），`-t 3` vs `-t 4` | 3.17 vs 4.16 tok/s | prefill 是计算密集，线程越多越快 |
| 权重重排 `--repack 0` vs `1`（`-t 3`） | pp32 3.18 vs 3.17；tg 1.91 vs 1.93 | 在 Pi 400（Cortex-A72，没有 dotprod 指令）上重排没有作用。所以 rpc-server 不做重排也不吃亏 |
| 单机直接跑 vs 通过本机 rpc-server 跑 | tg 1.93 vs 1.89 | RPC 本身的开销很小 |
| 2 台 TP，一次前向同时算 k 个 token（`-p 1,2,4,8,32 -n 0`） | k=1：342 ms；k=2：490 ms；k=4：820 ms；k=8：1504 ms；k=32：5.4 s | 2 台时一次多算几个 token 并不便宜（算 2 个要 1.43 倍时间），因为 Pi 的 CPU 在 batch>1 时很快变成计算瓶颈。所以投机解码（speculative decoding）在 2 台上收益有限。8 台时每台的计算只剩 1/8，同步开销不随 k 增加，预计会划算得多，待验证 |

### 第二轮优化尝试（2026-10-14 夜）

能在 2 台 Pi 和 Mac 模拟上验证的想法都试了，**只有确定更好、结果也正确的才采用**。

| 尝试 | 结果 | 决定 |
|---|---|---|
| OpenMP 线程等待策略（`OMP_WAIT_POLICY=active/passive`、`GOMP_SPINCOUNT`） | 2.86–2.90 vs 默认 2.94 tok/s | ✗ 不用 |
| 不用 OpenMP，改用 ggml 自带线程池（`GGML_OPENMP=OFF`） | 2.03 vs 2.91 tok/s，慢很多 | ✗ 不用 |
| 主控上 llama-bench 用 `-t 1/2/4` | 都是 2.94 | 无影响 |
| 小数据的同步直接在内存里相加（不再拷出拷入、不再单独启动加法计算图） | 每次同步的"本地加"从约 50 µs 降到约 17 µs；2 台整体速度在误差内（2.91–2.95）；台数越多次数越多，收益越大 | ✓ 已采用（a8cd154） |
| 同步算法 all-gather（一次发给所有 Pi，1 轮） | Mac 模拟（加 2 ms 延迟）：串行延迟次数 N=4 时 141 → 58–72，N=8 时 217 → 52；但每台发的数据是 (N-1) 倍，在真实千兆网上未必更快 | ◐ 做成开关 `GGML_RPC_COMM_ALGO=ag`，默认不开，明天 8 台实测（B01/B02） |
| 修复：初始化时监听队列只有 1、accept 没有超时 | 8 个 rank 同时连接时会卡死（Mac 模拟 8 台时复现）。改成队列 64 + accept 超时 130 秒 | ✓ 已采用（**上一版 c1212b5 在 8 台时有概率卡死，必须用 a8cd154**） |
| rpc-server `-c` 本地权重缓存 | 加载时间 32 → 17 秒；但台数一变就新增一份缓存，2 台时每台约 0.8 GB，会占满 cassian 的磁盘 | ◐ 脚本里默认关，`RPC_CACHE=1` 开启 |
| **快速模型：输出层从 Q6_K 改成 Q4_0** | 同一台主控（rex）上对比：2 台 TP **2.93 → 3.19 tok/s（+9%）**，单机 +4–5%；困惑度 8.08 → 8.13（+0.6%，在误差 ±0.27 内）；其他 254 个张量逐字节不变 | ◐ 改变了模型，所以作为可选项（`scripts/make_fast_model.sh`，rex 上已有）；阶段 A 的验证仍用原模型 |

**为什么输出层值得单独优化：** 计时日志显示，每个 token 最后一段计算（输出层，把隐藏状态变成 12.8 万个词的分数）在每台上要 **85 ms，占计算时间的 27%**，28 层 transformer 加起来才约 226 ms（每层 attention 约 2.2 ms、FFN 约 5.9 ms）。原因是这个模型的输出层和输入词表共用一个矩阵（`token_embd.weight`），它是 **Q6_K、323 MB，占模型的 18%**，而 Q6_K 在 Cortex-A72 上算得比 Q4_0 慢。

正确性检查（a8cd154）：
- 困惑度：2/4/8 节点、rd/ag 都和上一版完全一致（11.12 / 11.09 / 11.12）；
- 固定 `--temp 0` 逐 token 生成：上一版和 rd 生成的文字相同，ag 从中间开始措辞略有不同，内容都正常。这是浮点加法顺序不同造成的。

## 推到 8 台：Mac 上用 Docker 模拟（每个 rpc-server 一个容器，所有容器出口都加 2 ms 延迟）

Mac 上 8 个容器共用 10 个 CPU，所以这里的 tok/s **不能**代表 8 台 Pi 的速度。可信的是这两项"协议本身"的量：
- **每 token 串行网络延迟次数**（斜率）；
- **每 token 的总流量**。

| N | 模式 | 原版：串行延迟次数 / token | 改进版：串行延迟次数 / token | 原版：总流量 / token | 改进版：总流量 / token |
|---|---|---|---|---|---|
| 2 | TP | 157 | **70** | 4.1 MB | 4.1 MB |
| 4 | TP | 1406 | **141**（少 10 倍） | 144 MB | **12.7 MB** |
| 8 | TP | 4164 | **217**（少 19 倍） | 430 MB | **35.6 MB** |
| 2/4/8 | PP | 5 / 5 / 约 20 | 3 / 12 / 13 | 1.2–1.5 MB | 同左 |

模拟里 TP 的 tok/s：N=4 时 6.0 → 9.7（+60%），N=8 时 2.3 → 6.4（2.7 倍）。

a8cd154 的两种同步算法（加 2 ms 延迟时的串行延迟次数；Mac 上 CPU 争抢导致噪声较大）：

| N | rd（默认） | ag（`GGML_RPC_COMM_ALGO=ag`） |
|---|---|---|
| 4 | 115–188 | **58–72** |
| 8 | 247 | **52** |

改进版的正确性用困惑度检查（256 token 上下文，6 段）：

| 配置 | 困惑度 |
|---|---|
| 单机 | 11.13 |
| 改进版 TP，4 节点 | 11.09 |
| 改进版 TP，8 节点 | 11.12 |

差异来自 prefill 阶段大张量用 BF16 传输，这是上游原有的设计。原版 TP 在 4 节点上跑困惑度时会崩溃（`recv failed`），我们没有继续追查原因。

### 8 台 Pi 的粗略估算（还没有实测）

每 token 时间 ≈ 计算时间 + 串行延迟次数 × 单次延迟 + 每次同步的固定开销。按下面的参数估算：
- 计算时间 = 540 ms ÷ N；
- 单次延迟约 0.35 ms，即 ping 的一半；
- 每次同步的固定开销用 2 节点实测反推，大约 1–1.5 ms。

| 方案 | 估算速度 | 结论 |
|---|---|---|
| 原版 TP，8 台 | 4164 × 0.35 ms ≈ 1.5 s/token，**低于 1 tok/s** | 比一台还慢 |
| 改进版 TP，8 台 | 68 + 217 × 0.35 + 固定开销（56 次同步 × 3 步） ≈ 200–330 ms，**约 3–5 tok/s** | 有意义的提速 |
| PP，8 台 | 不超过 1.85 tok/s | 只为了装下更大的模型 |

## 优化方法汇总（按"用了值不值"排序）

1. **用我们 fork 的改进版做 TP**（a8cd154）：
   - 4/8 台时 Pi 之间直接交换数据：串行延迟次数少 10–19 倍，流量少 11–12 倍。这是能扩展到 8 台的前提；
   - 小数据直接在内存里相加；
   - 修复了 8 台时初始化可能卡死的问题。
2. **decode 时 rpc-server 用 `-t 3`**：零成本，2 台实测 +21–26%，单机也更快（原因是内存带宽，与台数无关）。prefill 用 `-t 4`。
3. **快速模型**（输出层 Q4_0）：+9%，困惑度只差 0.6%。可选。
4. **TP 的台数取 2、4、8，并且能整除 KV head 数**（Llama-3B 有 8 个 KV head，所以最多 8 台）。否则会退回经过主控中转的慢路径。用 Qwen-0.5B（只有 2 个 KV head）在 4 台和 8 台上跑就会这样。
5. **PP 只在模型单台装不下时用**：它不提升单个请求的速度。
6. **待 8 台实测决定**：同步算法 ag 还是 rd；一次算多个 token（批处理、投机解码）在 8 台上是否划算。
7. **试过、没有效果**：OpenMP 等待策略、不用 OpenMP、权重重排、主控 llama-bench 的线程数、PP 时主控算前半段层。
8. **没做、但下一步值得做**：
   - **减少每 token 57 段计算的切换开销**：2 台时每台的计算比理想值多约 20%；
   - **减少同步次数**：每层 2 次 allreduce 是 Megatron 式切分决定的；
   - **TP + PP 混合**：比如 8 台分成 2 组，组内 TP、组间 PP。
