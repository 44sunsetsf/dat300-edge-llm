# 实验报告：交换机 + 4 台 Pi 实测（2026-10-14）

本报告记录 2026-10-14 在实验室用 Netgear M4300 交换机连接 4 台树莓派（外加一块 LubanCat-5）做的实验：找出 TP 和 PP 的瓶颈，给出优化方法，并在真机上验证效果。所有数字都是当天实测的，原始日志在 `logs/`（文件名里带测试编号），复现命令见最后一节。

模型：Llama-3.2-3B-Instruct Q4_0（1.8 GB）。速度单位都是 token/秒：**prefill** 是处理 prompt 的速度（决定首 token 时间），**decode** 是逐字生成的速度。

## 一、结论

| | 瓶颈 | 优化 | 效果（4 台 Pi） |
|---|---|---|---|
| **TP** | ① 原版 llama.cpp 4 台以上时同步都经过主控中转，主控每 token 发 49.9 MB | 改 llama.cpp：Pi 之间直接 allreduce | decode 1.03 → 2.99 |
| | ② 输出层没有被切分：模型的输出层和输入嵌入共用一个矩阵（tied），llama.cpp 让每台都完整算一遍，每台每 token 80 ms，不随台数减少 | 给模型补一个独立的 `output.weight`（`scripts/untie_output.py`），输出层按台数切分；结果和原模型完全相同 | decode 2.99 → 4.85（**+62%**） |
| | ③ 计算变少后线程不再是限制 | rpc-server 从 3 线程改 4 线程 | decode 4.85 → **5.04**，prefill 10.1 → **12.6** |
| | **合计** | | **decode 1.03 → 5.04（4.9 倍），比单机 1.84 快 2.7 倍；prefill 4.14 → 12.6（单机的 3.0 倍）** |
| **PP** | 一个请求的各层只能一台接一台算，单请求 decode 和单机一样（1.84–1.88） | 原理决定，单请求无法提速 | — |
| | prompt 只有一块时，同一时刻只有一台在算 | 把 prompt 切成小块（`-ub 32`），llama.cpp 让各台同时处理不同的块 | prefill 4.16 → 4.68（+12%，理论上限约 2.3 倍，见 4.2） |
| | 多请求时每个 token 都要读一遍全部权重 | 同时处理多个请求（`llama-server -np 4`） | 总吞吐 1.83 → 3.2（4 个请求） |
| | 多请求 + 小块流水线（`-ub 2`），让 decode 也在各台之间流水线起来 | 8 个请求：3.24 → **4.18（+29%）**，唯一一个超过单机（3.46）的 PP 配置 |
| **网络** | Pi 用 DHCP 但交换机没开 DHCP，Pi 每 45 秒重置一次网口，实验经常中断 | 交换机开 DHCP、按 MAC 绑定 IP；Pi 本机也设固定 IP | 不再掉线，丢包 0%，往返 0.05–0.15 ms |
| **异构** | 通用程序（按 A72 编译）用不上 RK3588 的点积指令 | 给 A76 单独编译，绑定 4 个大核 | LubanCat-5 单机 decode 5.84 → **12.3**，prefill 7.5 → 48.8 |
| | 平均切分时快的板子要等慢的 Pi | `-ts` 按速度分配工作量（TP 也支持） | rex + cat 的 TP：3.24 → **7.00**；PP：3.07 → 5.52 |

几点要先说清楚：
- **TP 的两项代码/模型优化缺一不可**：只用 untied 模型不改代码是 1.09，只改代码不用 untied 是 2.99，两者一起是 4.85。
- **"同步次数多"不是交换机网络下的瓶颈**：把每次同步的轮数从 2 轮减到 1 轮（ag 算法），速度不变（4.85 vs 4.81）。之前在 Mac 上模拟时每次延迟设成了 2 ms，而真实交换机只有约 0.1 ms。
- **PP 不能让一个人的对话变快**，它的价值在于装下单台装不下的大模型，以及多请求时的吞吐。

- 交换机：Netgear M4300-28G，千兆，所有设备 1000 Mb 全双工。网络配置见 [`网络配置.md`](网络配置.md)。
- 软件：改进版 llama.cpp `a8cd154`（fork 的 `dat300` 分支），原版 `bd4eeaa`。Pi 用按 `-mcpu=cortex-a72` 静态编译的包，cat 用 `-mcpu=cortex-a76` 的包。
- 测速：`llama-bench -p 32 -n 30 -r 2`（另注的除外），每组测试前重启所有 rpc-server。整个实验期间所有 Pi 都没有降频（`throttled=0x0`）。

## 三、网络：先解决"时断时续"

一开始 Pi 一会儿在线一会儿掉线。查 han 的 NetworkManager 日志发现：Pi 的有线连接是 DHCP，交换机出厂没有开 DHCP。NetworkManager 每等 45 秒拿不到地址，就判定连接失败，把网口整个重置一次，手动加的地址也会被清掉。

解决办法（两层保险）：
1. 交换机：开 DHCP 服务，按 MAC 给每台 Pi 分配固定地址；管理地址设为 10.77.0.1；保存配置。新 Pi 插上会自动拿到 .101–.199 的地址。
2. 每台 Pi：有线连接改成固定 IP（`ipv4.method manual`），组员原来的 10.0.0.x 保留。这样就算交换机的 DHCP 出问题，也不影响实验。

改完以后实验期间再也没有掉线。Pi 之间 ping 丢包 0%，往返 0.05–0.15 ms。用 10.77.0.0/24 而不是 10.0.0.x，是因为笔记本连的 Wi-Fi 也在 10.0.x.x，会冲突。

## 四、TP（张量并行）

### 4.1 瓶颈①：原版的同步要经过主控中转

| 4 台 TP（原模型） | prefill | decode | 主控每 token 收 / 发 |
|---|---|---|---|
| 原版 bd4eeaa | 5.77 | 1.03 | 4.4 MB / **49.9 MB** |
| 改进版 a8cd154 | 9.68 | **2.99** | 1.5 MB / 1.6 MB |

原版只有恰好 2 台时才让 Pi 之间直接交换数据。4 台时每个 token 的 56 次同步都要先把数据发给主控，主控加好再发回去，主控的网卡和往返次数成了单点瓶颈。原版 4 台（1.03）甚至比单机（1.84）还慢。改进版让任意 2/4/8/16 台之间直接做 allreduce（递归倍增），decode 提高到 2.9 倍。2 台时两者差不多（2.86 vs 3.00），因为原版 2 台本来就是直接交换的。

### 4.2 瓶颈②：输出层没有被切分（今天的新发现）

改进版 4 台的 decode（2.99）和 2 台（3.00）几乎一样，台数翻倍却没有变快。用计时日志（`GGML_RPC_TRACE`，见 [`计时日志.md`](计时日志.md)）拆开每个 token 的时间：

| 每台每 token（ms） | 每层的计算 | 最后的输出层 | 计算合计 | 同步（含等别人） | 总时间 |
|---|---|---|---|---|---|
| finn / han / luthen（原模型） | 2.0 | **80–85** | 190–205 | 108–126 | 342 |
| rex（主控，原模型） | **3.8** | 85 | **297** | 26 | 342 |
| finn / han / luthen（untied） | 2.0 | **20** | 131–140 | 31–40 | 207 |
| rex（主控，untied） | 2.1 | 22 | 141 | 30 | 207 |

数据来自 `logs/trace/tp_4n_opt_B10_tp4_trace_*` 和 `logs/trace/tp_4n_opt_U1_untied_*`。

问题有两个：
1. **输出层（词表 128256 × 3072，Q6_K，323 MB）每台都完整算了一遍**，4 台时每台还是 80–85 ms，和 2 台时一样。原因在 llama.cpp 的切分规则（`src/llama-model.cpp` 里的 `llama_meta_device_get_split_state`）：`output.weight` 会按词表维度切开，但 Llama-3.2 没有 `output.weight`，输出层直接复用 `token_embd.weight`，而 `token_embd` 属于"其他张量"，每台存一整份、每台都完整计算。
2. **主控 rex 每层慢将近一倍**（3.8 vs 2.0 ms），大家每个 token 要等它约 100 ms。最初怀疑是 luthen（Pi 4B）或主控上的 llama-bench 抢资源，但把主控的 rpc-server 改成 2 线程以后 rex 还是 290 ms。换成 untied 模型以后这个现象也消失了，所以它和问题 1 是同一个根源。

**优化：**`scripts/untie_output.py` 给模型补一个 `output.weight`，内容就是 `token_embd` 的拷贝，量化类型不变。这样输出层就能按台数切分，每台只算 1/4。模型文件大 323 MB（2.25 GB）。

**正确性：**在 cat 上用同一段文本（llama.cpp 的 README 和 build 文档，256 token × 12 段）算困惑度，原模型和 untied 模型**每一段都完全相同**（最终 7.2208 ± 0.54），说明计算结果没有变化。

**效果：**

| | 原版 | 改进版 |
|---|---|---|
| 原模型（tied） | 1.03 | 2.99 |
| untied 模型 | 1.09 | **4.85** |

原版用 untied 也没用，因为它被瓶颈①卡住；两项一起才有 4.85。untied 以后每台的输出层从 80 ms 降到 20 ms（正好 1/4），主控和 worker 的计算时间也一样了（131–141 ms）。

### 4.3 其他调整

| 4 台 TP，untied | prefill | decode | 说明 |
|---|---|---|---|
| rpc-server 3 线程 | 10.07 | 4.85 | |
| **rpc-server 4 线程** | **12.57** | **5.04** | 计算变少以后，4 线程反而更快（原模型时 3 线程最快） |
| 3 线程 + ag 同步算法 | 10.01 | 4.81 | 同步轮数从 2 减到 1，没有变化 → 交换机下同步延迟不是瓶颈 |
| 3 线程，prompt 512 + 生成 128 | 9.99 | 4.93 | 长输出时也稳定（原模型同样条件 2.93） |
| 2 台，3 线程 | 5.98 | 3.45 | 2 台时 untied 也有 +15%（3.00 → 3.45） |
| 快速模型（输出层改 Q4_0，tied），3 线程 | 9.78 | 3.25 | 只减轻输出层，不切分，效果远不如 untied |

### 4.4 TP 还剩什么

untied 以后 4 台每 token 207 ms：计算约 135 ms（每层 2 ms × 55 段 + 输出层 20 ms），同步约 35 ms，空等主控约 33 ms（主控采样、取 logits、发下一个 token 的输入）。

- 计算部分随台数线性下降；
- 同步部分每多一倍台数多一轮交换（每轮约 0.1 ms × 56 次）；
- "空等主控"不随台数变化，台数越多占比越大。

粗略推算 8 台：计算约 70 ms、同步约 45 ms、空等约 33 ms，合计约 150 ms，**decode 约 6.5 tok/s**，需要实测验证。

## 五、PP（流水线并行）

### 5.1 瓶颈：单个请求的各层只能一台接一台地算

| 配置 | prefill（32 token） | decode |
|---|---|---|
| 单机 | 4.14 | 1.84 |
| PP 2 台 | 4.12 | 1.88 |
| PP 3 台 | 4.07 | 1.83 |
| PP 4 台 | 4.01 | 1.84 |

PP 把 28 层分成几段，每台一段。生成一个 token 时数据依次经过每一台，同一时刻只有一台在算，所以总时间等于单机把所有层算一遍。PP 本身的网络开销几乎为零：主控每 token 只收约 0.5 MB（最后一台送回的 logits），4 台比单机只慢 0–3%。**结论：单个请求的 PP 不可能比单机快，这是原理决定的。** 下面两项优化针对的是长 prompt 和多请求。

### 5.2 优化①：切块流水线 prefill

把 prompt 切成几块（`-ub` = 每块的 token 数），第 1 台算第 2 块的同时，第 2 台算第 1 块。llama.cpp 支持这种流水线：所有设备都支持异步计算和事件时会自动开启，RPC 后端满足条件，日志里能看到 `pipeline parallelism enabled`。

| prompt 128 token | prefill | 说明 |
|---|---|---|
| 单机，`-ub 32` | 4.13 | 单机切块不影响速度（`-ub 512` 是 4.06），作对照 |
| PP 4 台，`-ub 128`（整段一块） | 4.16 | 没有流水线 |
| **PP 4 台，`-ub 32`（切成 4 块）** | **4.68（+12%）** | 有流水线 |

流水线确实起作用了，但只有 +12%。理论上 4 块分给 4 台，时间从"4 块 × 4 段"变成"(4+3) 个时间片"，约 2.3 倍。差距的可能原因（推测，还没用计时日志验证）：相邻两段之间的激活值要经过主控中转（从上一台 `get_tensor` 再 `set_tensor` 给下一台），这一步要等上一台算完，所以实际的重叠很少。如果确实如此，要真正发挥 PP 流水线，就需要让 rpc-server 之间直接传激活值，不经过主控，就像我们在 TP 里对 allreduce 做的那样。这是下一步可以改的地方。

### 5.3 优化②：同时处理多个请求

`llama-batched-bench -npp 32 -ntg 16 -npl 1,4,8`：同时处理 1、4、8 个请求，每个请求 32 token prompt、生成 16 token。表里是生成阶段所有请求加起来的吞吐（tok/s）：

| 同时处理的请求数 | 单机 | PP 4 台 | TP 4 台（untied，4 线程） |
|---|---|---|---|
| 1 | 1.85 | 1.83 | 4.26 |
| 4 | 3.40 | 3.17 | 6.46 |
| 8 | 3.46 | 3.24 | **7.83** |
| 8，PP 用 `-ub 2`（见 5.4） | | **4.18** | |

- 同时处理多个请求时，单机和 PP 的总吞吐都提高到约 1.8 倍。Pi 的瓶颈是内存带宽，读一遍权重可以顺便多算几个请求。
- PP 的多请求吞吐和单机差不多（每次还是只有一台在算），所以 PP 并不比单机更擅长多请求。
- TP 在多请求时同样受益：8 个请求时 7.83，是单机的 2.3 倍。**同时服务多人时，TP 也比 PP 好得多。**
- 注：这里的单请求 TP（4.26）比 llama-bench 的 5.04 低，因为测试很短（每个请求只生成 16 token），固定开销占比大。

### 5.4 优化③：多请求 + 小块，让 decode 也流水线起来

8 个请求、每块 2 个请求（`-ub 2`），这样 decode 每一步被切成 4 块，可以同时在 4 台上算。

| PP 4 台，8 个请求 | 生成阶段总吞吐 |
|---|---|
| 不切块（一块 8 个） | 3.24 |
| **切成 4 块（`-ub 2`）** | **4.18（+29%）** |
| 对照：单机 8 个请求 | 3.46 |

decode 流水线的效果比 prefill 流水线好（+29% vs +12%），而且这是唯一一个让 PP 超过单机的配置（4.18 vs 3.46）。代价是每块变小以后，"读一遍权重多算几个请求"的好处变少了，所以离理论上限（4 倍）还很远。

### 5.5 PP 小结

| PP 的用途 | 能不能优化 | 实测 |
|---|---|---|
| 一个人对话（单请求 decode） | 不能，原理决定 | 和单机一样（1.84） |
| 长 prompt 的首 token 时间 | 能：切块流水线 | +12%（`-ub 32`）；要更多需要改 llama.cpp，让 rpc-server 之间直接传激活值 |
| 同时服务多人 | 能：多请求 + 小块流水线 | 3.24 → 4.18（+29%），超过单机 |
| 装下单台装不下的大模型 | 这是 PP 真正的价值 | 本次没测（需要更大的模型） |

在 Pi 这种内存小、算力弱、网络很快的集群上，**TP 在所有指标上都比 PP 好**：单请求 decode 5.04 vs 1.84，prefill 12.6 vs 4.7，8 个请求的吞吐 7.83 vs 4.18。PP 只在模型大到 TP 也放不下时才有意义（TP 每台也只存 1/N 的权重，所以这种情况很少见）。

## 六、异构设备：LubanCat-5（cat）

### 6.1 单机：编译参数决定一切

| cat 单机 | prefill | decode |
|---|---|---|
| 通用版（`-mcpu=cortex-a72`），4 个大核 | 7.48 | 5.84 |
| A76 版（`-mcpu=cortex-a76`），8 核（大小核一起） | 47.44 | 10.12 |
| **A76 版，绑定 4 个大核（`taskset -c 4-7 -t 4`）** | **48.75** | **12.28** |

- A72 没有点积指令（`asimddp`），A76 有。Q4_0 矩阵乘法用点积指令快很多：prefill 6.5 倍，decode 2.1 倍。
- 加上小核（A55）反而变慢 18%：TP 和多线程都要等最慢的线程。
- `setup_pi.sh` 现在会自动识别 A76，安装 A76 版；`run_bench.sh` 会自动把 rpc-server 绑到大核上。
- **cat 一台的 decode（12.3）就比 4 台 Pi 的 TP 集群（5.04）还快。**

### 6.2 cat 和 Pi 混用

cat 的单机速度是 Pi 的 6.7 倍。平均切分时，大家都要等最慢的 Pi；`-ts` 可以按比例给每台分配不同的工作量（顺序和 `-dev` 一致）。

| 配置（主控都是 rex） | prefill | decode | 说明 |
|---|---|---|---|
| TP rex + cat，平均切分 | 7.71 | 3.24 | cat 算完自己那一半只要 65 ms，然后等 rex 200 ms（计时日志 H01） |
| **TP rex + cat，`-ts 1/4`** | **17.17** | **7.00** | **TP 也支持不均匀切分**，2.2 倍 |
| PP rex + cat，平均切分 | 6.25 | 3.07 | |
| PP rex + cat，`-ts 1/6` | 10.57 | 5.52 | |
| TP cat + 3 台 Pi，平均切分（untied） | 12.28 | 4.57 | 还不如 4 台 Pi（5.04）：平均切分时大家都等最慢的 Pi，cat 的优势用不上（为什么还略慢没有细查） |
| PP cat + 3 台 Pi，`-ub 32`，平均切分 | 6.07 | 2.12 | |
| PP cat + 3 台 Pi，`-ub 32`，`-ts 1/12/1/1` | 13.12 | 3.47 | |
| 对照：cat 单机 | 48.75 | 12.28 | |

结论：
1. **异构集群一定要按速度设 `-ts`**：TP 2 台从 3.24 提到 7.00，PP 从 3.07 提到 5.52。
2. 但这个模型 cat 一台就装得下，**任何和 Pi 混用的配置都不如 cat 单独跑**（12.3）。Pi 太慢，混进集群反而拖后腿。异构只在模型大到 cat 一台装不下时才有意义，这时按速度设 `-ts`，让 cat 多分。
3. 对 8 台 Pi 的集群来说，**买一块 RK3588 的板子比加 Pi 划算得多**。

## 八、原始数据

- 每组测试一个日志：`logs/<模式>_<台数>n_<版本>_<测试编号>_<时间>.log`，最后一行是 `RESULT`（多请求测试是 `BATCHED_DONE`）。测试编号：A03–A10 和 B02–B10 是阶段 A/B（原模型），T01–T08 是 TP + untied，P01–P14 是 PP，H01–H08 是异构，U1 是第一次 untied 测试，X2 是主控 2 线程。
- 计时日志：`logs/trace/` 下的 B10（原模型）、U1（untied 4 台）、T05（untied 2 台）、X2。
- 批量运行的输出：`logs/session_4pi_switch.out`、`logs/study_1014*.out`。
