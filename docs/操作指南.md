# 操作指南：4/8 台 Pi 集群跑 Llama-3.2-3B，并验证优化效果

目标：
1. 把所有 Pi 装好我们的改进版 llama.cpp，整个集群一起跑模型；
2. 用 8 台（或 4 台）验证 [`RESULTS.md`](RESULTS.md) 里的结论和预测；
3. 有时间再做"探索"部分。

所有命令都在**一台笔记本（下面叫"控制机"）**上运行，通过 ssh 操作 Pi。控制机建议用 Mac 或 Linux；Windows 请用 WSL。整个过程不需要在 Pi 上手动敲命令。

---

## 0. 出发前（控制机，有网的地方，5 分钟）

```bash
git clone https://github.com/44sunsetsf/dat300-edge-llm.git
cd dat300-edge-llm
scripts/setup_pi.sh --download-only     # 把 llama.cpp 安装包（约 100 MB）下载到 dist/，现场就不需要外网
```

**模型**：只有 HEAD 那台需要模型文件（Llama-3.2-3B-Instruct-Q4_0.gguf，1.9 GB），WORKER 不需要。
- cassian 上已经有模型，**建议用 cassian 当 HEAD**；
- 如果要用别的 Pi 当 HEAD，就在有网的地方把模型下载到控制机的 `../models/` 目录（也就是和 `dat300-edge-llm` 同级的 `models` 文件夹），`setup_pi.sh --model` 会从控制机复制过去：
  ```bash
  mkdir -p ../models && curl -L -o ../models/Llama-3.2-3B-Instruct-Q4_0.gguf \
    https://huggingface.co/bartowski/Llama-3.2-3B-Instruct-GGUF/resolve/main/Llama-3.2-3B-Instruct-Q4_0.gguf
  ```

## 1. 接线、开机、确认 IP

交换机和 IP 怎么配，大家按自己习惯的方式来。只要满足下面三条就行：
- **控制机能 ssh 到每台 Pi**（控制机也插到交换机上，或者在同一个网络里）；
- **Pi 之间能互相访问 50052 和 51052 端口**：50052 是 rpc-server，51052 是我们的改进版里节点之间直接交换数据用的；
- 所有 Pi 都用**有线网口**（千兆）。不要用 Wi-Fi，Wi-Fi 的延迟会让 TP 慢很多。

## 2. 填写 Pi 列表

```bash
cp scripts/hosts.env.example scripts/hosts.env
# 编辑 scripts/hosts.env：
#   HEAD=cassian@<IP>                                       ← Pi 400、内存 4G、有模型的那台
#   WORKERS="rex@<IP> 用户@<IP> 用户@<IP> ..."              ← 其余 7 台（4 台集群就是 3 台）
```

TP 的台数要用 **2、4 或 8**：我们的改进版只支持 2 的幂，其他台数（比如 6）会退回经过 HEAD 中转的慢路径。

`WORKERS` 的**顺序有意义**：测 4 台时用的是 HEAD 加上前 3 个 WORKERS。所以和 HEAD 型号相同的 Pi 要排在前面，型号不一样的放最后（原因见第 9 节）。

## 3. 免密登录（每台输入一次密码）

```bash
scripts/add_keys.sh
```

## 4. 安装（全部 Pi 并行，约 1 分钟）

```bash
scripts/setup_pi.sh --model
```

每台 Pi 上会装两个版本，两个版本互不影响，对 Pi 原来的东西（distributed-llama、原有的模型文件等）也没有影响：
- `~/llama.cpp/build/bin/`：**改进版**，默认用这个；
- `~/llama.cpp/build-stock/bin/`：**原版**，用来对照。

脚本会自动适配：Debian 13 装默认版；Debian 12 装兼容版；32 位系统会报错，这种 Pi 要用 Raspberry Pi Imager 重装 64 位系统。

> 有的 Pi 以前在 `~/llama.cpp` 里自己编译过 llama.cpp。安装会替换掉其中的 `build/` 目录，源码不动。

## 5. 体检

```bash
scripts/check_cluster.sh
```

每台一行，有问题的项会标 `!!`。**所有行都没有 `!!` 再继续。** 常见的问题：
- **版本不对**：重新运行 `scripts/setup_pi.sh`；
- **有残留进程**：ssh 上去执行 `pkill -x ggml-rpc-server`，dllama 也要停掉。测量期间 Pi 上不能跑别的重活；
- **降频标志不是 0x0**：供电不足（换个好电源）或过热。这台的结果会偏慢，最好先换掉；
- **网口不是 1000Mb**：网线或交换机端口有问题。

## 6. 先让集群跑起来（冒烟测试）

```bash
NN=2 scripts/chat.sh "用一句话介绍哥德堡"   # 先用 2 台试
scripts/chat.sh "用一句话介绍哥德堡"        # 全部 Pi 一起（TP，改进版）
scripts/chat.sh                              # 交互对话，Ctrl+C 退出
```

最后一行会显示 `Generation: x t/s`。参考值：2 台约 2.8–2.9。

## 7. 核心验证（约 60–80 分钟，可以中断后接着跑）

```bash
scripts/exp/session_8pi.sh A
```

阶段 A 会依次跑下面这些（重要的排在前面），每组重复 2 次：

| 项目 | 内容 |
|---|---|
| A01 / A02 | 8 台 TP，改进版 vs 原版（rpc-server 都用 3 线程） |
| A03 / A04 | 4 台 TP，改进版 vs 原版 |
| A05 / A06 | 2 台 TP，改进版 vs 原版 |
| A07 | 单机基线 |
| A08–A10 | 8 / 4 / 2 台 PP |

几点说明：
- 原版在 4 台和 8 台时可能非常慢甚至卡住，每组都有超时（20 分钟），超时会自动跳到下一组；
- 断了就重新运行同一条命令，已经完成的组会跳过；
- 要重跑某一组，删掉 `logs/.done_<项目名>`。

跑完生成结果表，填进 [`RESULTS.md`](RESULTS.md) 的"8 台实测"一节：

```bash
python3 scripts/summarize.py            # 打印表格，同时写入 logs/summary.md
```

**判断标准（我们的预测，见 RESULTS.md）**：
- 8 台 TP：改进版明显快于原版，预测约 3–5 tok/s；原版低于 1 tok/s，可能比单机还慢；
- 4 台 TP：改进版快于原版；
- PP：台数越多 decode 不会变快，始终不超过单机的 1.85 tok/s；
- 如果改进版在 8 台时比 2 台还慢，说明"每次同步的固定开销"占了主导，这也是一个有价值的发现。

## 8. 有时间再做

```bash
scripts/exp/session_8pi.sh B            # 线程数的影响（约 20 分钟）
PI_SUDO_PW=<Pi的sudo密码> scripts/exp/session_8pi.sh C   # 网络延迟敏感度（约 30 分钟）
```

- **阶段 B**：rpc-server 用 4、3、2 线程，以及只给 HEAD 那台设 3 线程，各跑一次。
- **阶段 C**：给每台 Pi 的网口加 1 ms 延迟后再测，用来算"每个 token 有多少次串行的网络延迟"。
  - 计算方法：`(加延迟后的 ms/token − 不加时的 ms/token) ÷ 1 ms`，这就是每 token 的串行延迟次数；
  - 结果可以和 RESULTS.md 里 Mac 模拟的数字比较；
  - 跑完脚本会自动撤掉延迟。手动撤掉的命令是 `PI_SUDO_PW=... scripts/exp/netem.sh 0`。

### 探索方向（单独跑某一组用 `scripts/run_bench.sh`，参数见脚本开头的注释）

```bash
NN=8 RPC_T=3 scripts/run_bench.sh tp                       # 任意一组
NN=8 RPC_T=3 P=512 N=30 scripts/run_bench.sh tp            # 长 prompt：看首 token 时间（prefill）
NN=8 RPC_T=3 ENV=GGML_RPC_NO_COMM=1 scripts/run_bench.sh tp   # 关掉节点间直接交换，所有数据都经过 HEAD
NN=4 RPC_T=3 EXTRA="-ts 1/1/1/0.8" scripts/run_bench.sh tp    # 不均匀切分（TP 下是否生效待验证）
```

可以考虑的问题：
1. **prefill 和 decode 的最佳线程数不一样**：`-t 3` 让 decode 快约 20%，但 prefill 慢约 22%。8 台时还是这样吗？
2. **台数和速度的关系**：2→4→8 台，改进版 TP 的速度曲线是什么样的？从第几台开始收益变小？
3. **更大的模型**：比如 Qwen3-8B Q4_0（约 4.7 GB），一台装不下，只有集群能跑。需要先把模型放到 HEAD，再设 `MODEL=~/路径` 运行。KV head 数要能被台数整除，否则会退回经过 HEAD 中转的慢路径。
4. **PP 同时处理多个请求时的吞吐**：用 `llama-server -np 4`。PP 单个请求不快，但可能适合同时服务多个用户。

## 9. 型号不一样怎么办

- TP 把每一层平均分给所有 Pi，**大家都要等最慢的那台**。混进一台 Pi 4（1.5 GHz）或者降频的 Pi，整个集群就按它的速度走。
- 做法：
  1. 核心验证（第 7 节）只用同型号的 Pi：在 hosts.env 里把它们排在前面，用 `NN=4` 或 `NN=8` 选；
  2. 型号不一样的 Pi 留到探索阶段，试试"不均匀切分"：`EXTRA="-ts 1/1/1/0.8"`，给慢的那台少分一点；
  3. `check_cluster.sh` 会显示每台的型号、CPU 频率和内存。
- HEAD 一定要用内存 4G 以上的 Pi，因为它要读入整个模型文件。WORKER 只拿 1/N 的权重，内存 2G 的也够。

## 10. 常见问题

| 现象 | 原因和处理 |
|---|---|
| `rpc-server 启动失败` | 端口被占用（上一次没退出）。运行 `ssh 用户@IP pkill -x ggml-rpc-server` |
| TP 卡在加载阶段不动 | 节点之间 51052 端口不通（防火墙或网络隔离），或者某台的 rpc-server 挂了。先 `check_cluster.sh`，再看那台 Pi 上的 `~/exp/logs/rpc.log` |
| 某一组结果是"失败" | 看 `logs/` 里对应的日志。原版多节点卡住超时属于预期结果，记录下来就行 |
| 速度比预期慢很多 | 有 Pi 在降频（体检里 `!!`）、有 Pi 走的是 Wi-Fi，或者有 Pi 在跑别的程序 |
| `summarize.py` 没有某一组 | 这组没有生成 RESULT 行（中途被中断了），删掉对应的 `.done` 标记后重跑 |

   ```bash
   for h in $(source scripts/hosts.env; echo $HEAD $WORKERS); do ssh $h pkill -x ggml-rpc-server; done
   ```
