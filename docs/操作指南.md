# 操作指南：4/8 台 Pi 集群跑 Llama-3.2-3B，并验证优化效果

目标：
1. 所有 Pi 装好我们的改进版 llama.cpp，整个集群一起跑模型；
2. 用 8 台（或 4 台）验证 [`RESULTS.md`](RESULTS.md) 里的结论和预测；
3. 有时间再做"探索"部分。

> 只想装好以后自己手动调参、不用实验脚本：做完下面第 0–5 步（安装和体检），然后看 [`手动使用改进版.md`](手动使用改进版.md)。

---

## 先搞清楚：有三种角色

| 角色 | 是哪台 | 要准备什么 | 要不要在上面敲命令 |
|---|---|---|---|
| **笔记本** | 我们自己的一台电脑（Mac 或 Linux；Windows 用 WSL），只要一台 | 本仓库、终端 | **要，所有命令都在这里敲** |
| **主控 Pi（HEAD）** | 选 1 台 Pi，**建议用 rex** | 模型文件（rex 上已有原模型和 **untied 模型**，默认用后者）+ llama.cpp 程序 | 不用（由笔记本远程操作） |
| **worker Pi** | 其余的 Pi（8 台集群就是 7 台） | 只要 llama.cpp 程序（`ggml-rpc-server`），**不需要模型** | 不用（由笔记本远程操作） |

```
          笔记本（敲命令）
              │ ssh
   ┌──────────┴──────────────── 交换机 ───────────────────────┐
   │                                                          │
 主控 Pi (HEAD)        worker Pi      worker Pi   ...   worker Pi
 有模型文件            无模型          无模型               无模型
 跑 llama-bench / llama-cli
 + 自己的 rpc-server   rpc-server     rpc-server           rpc-server
```

工作方式：
- **笔记本**通过 ssh 让每台 Pi 启动 `rpc-server`；
- **主控**读取模型，把每台该分到的权重通过网线发过去（每次启动都发一次，8 台时约 15–20 秒）；
- 然后所有 Pi 一起计算。主控自己也算一份，所以 8 台集群 = 1 台主控 + 7 台 worker。

> **下面所有命令都在笔记本的终端里、本仓库的目录（`dat300-edge-llm`）下运行。**整个过程不需要登录到 Pi 上敲命令；只有排查问题时才需要（会特别注明【在 Pi 上】）。

---

## 第 0 步：出发前准备 —— 【在笔记本上】，需要有网，约 5 分钟

```bash
git clone https://github.com/44sunsetsf/dat300-edge-llm.git
cd dat300-edge-llm
scripts/setup_pi.sh --download-only
```

最后一条命令把 llama.cpp 安装包（约 100 MB）下载到笔记本的 `dist/` 文件夹。之后安装时，笔记本直接把它推给每台 Pi，**现场的 Pi 不需要能上网**。

**只有不用 rex 当主控时才需要做：** 把模型也下载到笔记本上。之后安装时，笔记本会把它复制到主控 Pi。

```bash
mkdir -p ../models && curl -L -o ../models/Llama-3.2-3B-Instruct-Q4_0.gguf \
  https://huggingface.co/bartowski/Llama-3.2-3B-Instruct-GGUF/resolve/main/Llama-3.2-3B-Instruct-Q4_0.gguf
```

模型会存到和 `dat300-edge-llm` 同级的 `models` 文件夹，大小 1.9 GB。

## 第 1 步：接线、开机 —— 【在现场】

**实验室的 Netgear M4300 交换机已经配好了**：网段 10.77.0.0/24，交换机按 MAC 给登记过的 Pi 分配固定 IP（finn .2、han .3、rex .4、luthen .5、cassian .7），新 Pi 插上会自动拿到 .101–.199 的地址。IP 对照表、怎么登记新 Pi、笔记本怎么接，见 [`网络配置.md`](网络配置.md)。

需要满足这三条：

1. **笔记本能 ssh 到每台 Pi**：笔记本也用网线插到交换机上（会自动拿到 10.77.0.1xx 的地址）。可以在笔记本上用 `ssh 用户名@IP` 试一台。
2. **Pi 之间能互相访问 50052 和 51052 端口**：50052 给 rpc-server 用，51052 给改进版里 Pi 之间直接交换数据用。普通交换机默认就是通的。
3. **每台 Pi 都用网线**（千兆）。不要用 Wi-Fi，Wi-Fi 的延迟会让 TP 慢很多。

把每台 Pi 的**用户名和 IP** 记下来，第 2 步要用。

## 第 2 步：填写 Pi 列表 —— 【在笔记本上】

```bash
cp scripts/hosts.env.example scripts/hosts.env
```

然后用任意文本编辑器打开 `scripts/hosts.env`，改成现场的用户名和 IP：

```bash
HEAD=rex@10.77.0.4                                                  # 主控 Pi：用 rex（模型已经在上面）
WORKERS="finn@10.77.0.2 pi@10.77.0.3 pi@10.77.0.5 cassian@10.77.0.7 ..."   # 其余 Pi，用空格分开
```

用户名和 IP 见 [`网络配置.md`](网络配置.md) 的对照表；没登记的新 Pi，IP 在交换机上 `show ip dhcp binding` 查。

- TP 的台数要用 **2、4 或 8**：改进版只支持 2 的幂，比如 6 台会退回经过主控中转的慢路径。
- **WORKERS 的顺序有意义**：测 4 台时用的是主控加上前 3 个 worker。和主控型号相同的 Pi 排在前面，型号不一样的放最后（原因见第 9 节）。

## 第 3 步：设置免密登录 —— 【在笔记本上】，每台 Pi 输一次密码

```bash
scripts/add_keys.sh
```

脚本会逐台提示"请输入密码"，输入那台 Pi 的登录密码。之后所有脚本都不用再输密码。

## 第 4 步：给所有 Pi 安装 llama.cpp —— 【在笔记本上】，约 1 分钟

```bash
scripts/setup_pi.sh --model
```

- 笔记本把程序同时推给所有 Pi（主控和 worker 都装）；
- `--model` 会检查**主控**上的模型。rex 上已经有了，校验约 30 秒；没有的话，从笔记本的 `../models/` 复制过去。

装完以后**每台 Pi** 上都有两个版本：
- `~/llama.cpp/build/bin/`：**改进版**，默认用它；
- `~/llama.cpp/build-stock/bin/`：**原版**，做对照用。

安装不会动 Pi 上原来的东西（distributed-llama、原有的模型文件等）。

每台输出"可以运行"就成功了。如果某台报"32 位"，那台要用 Raspberry Pi Imager 重装 64 位系统，或者先不用它。

## 第 5 步：体检 —— 【在笔记本上】

```bash
scripts/check_cluster.sh
```

每台 Pi 输出一行，有问题的项标 `!!`。**所有行都没有 `!!` 再继续。** 常见的问题：

| 标了 !! 的项 | 怎么处理 |
|---|---|
| 版本 | 【在笔记本上】重新运行 `scripts/setup_pi.sh` |
| 残留进程 | 那台 Pi 上还在跑别的程序。【在笔记本上】运行 `ssh 用户名@IP pkill -x ggml-rpc-server`；如果是 dllama，也要停掉 |
| 降频标志 | 供电不足（换电源）或过热，这台会拖慢整个集群，最好先换掉 |
| 网口不是 1000Mb | 换根网线或换个交换机端口 |
| SSH 连不上 | 检查 IP 和用户名，以及第 3 步是否成功 |

## 第 6 步：让集群跑起来 —— 【在笔记本上】

```bash
NN=2 scripts/chat.sh "用一句话介绍哥德堡"     # 先用主控 + 1 台 worker 试
scripts/chat.sh "用一句话介绍哥德堡"          # 所有 Pi 一起
scripts/chat.sh                                # 交互对话，Ctrl+C 退出
```

- `NN=2` 表示只用 2 台，不写就是全部；
- 回答的最后会显示 `Generation: x t/s`，这就是生成速度。参考值：2 台约 2.8–2.9；
- 加载模型要等 20–40 秒，这是主控在给 worker 发权重。

## 第 7 步：核心验证实验 —— 【在笔记本上】，约 60–80 分钟

```bash
scripts/exp/session_8pi.sh A
```

这条命令会依次跑完下面所有组，不用手动一组一组跑。每组重复 2 次，重要的排在前面：

| 组 | 内容 |
|---|---|
| A01 / A02 | 8 台 TP，改进版 vs 原版（rpc-server 都用 3 线程） |
| A03 / A04 | 4 台 TP，改进版 vs 原版 |
| A05 / A06 | 2 台 TP，改进版 vs 原版 |
| A07 | 单机基线（只用主控） |
| A08–A10 | 8 / 4 / 2 台 PP |

- **笔记本不能睡眠，终端窗口别关**，否则实验会中断；
- 中断了不要紧：重新运行同一条命令，已经完成的组会自动跳过；
- 原版在 4 台和 8 台时可能非常慢甚至卡住，每组最多等 20 分钟，超时就自动跳到下一组。这本身也是结果，记录下来就行；
- 要重跑某一组：删掉笔记本上的 `logs/.done_<组名>` 文件，再运行一次。

跑完生成结果表：

```bash
python3 scripts/summarize.py
```

表格会显示在终端里，同时保存到 `logs/summary.md`。把数字填进 [`RESULTS.md`](RESULTS.md) 的"8 台实测"一节。

**怎么判断结果（我们的预测）：**
- 8 台 TP：改进版明显快于原版，预测约 3–5 tok/s；原版低于 1 tok/s，可能比单机还慢；
- 4 台 TP：改进版快于原版；
- PP：台数越多，decode 也不会变快，始终不超过单机的 1.85 tok/s；
- 如果改进版在 8 台时反而比 2 台慢，说明"每次同步的固定开销"占了主导，这也是一个有价值的发现。

## 第 8 步（有时间再做）：更多实验 —— 【在笔记本上】

```bash
scripts/exp/session_8pi.sh B
PI_SUDO_PW=Pi的sudo密码 scripts/exp/session_8pi.sh C
```

- **B：各项优化的对比**（约 40–60 分钟）。都和阶段 A 的 A01/A03（8/4 台，改进版，默认设置）比：

  | 组 | 内容 | 要回答的问题 |
  |---|---|---|
  | B01 / B02 | 8 / 4 台，同步算法改成"一次发给所有 Pi"（`GGML_RPC_COMM_ALGO=ag`） | Mac 模拟里 ag 的串行延迟次数少 2–4 倍，但它发的数据多，真实千兆网上哪种快？ |
  | B03 / B04 | 8 台，rpc-server 用 4 线程 / 只有主控用 3 线程 | 3 线程更快的结论在 8 台时还成立吗？ |
  | B05–B07 | 8 / 4 / 2 台，用"快速模型"（输出层改成 Q4_0） | 2 台快 9%，8 台呢？主控上要有快速模型：rex 上已经有了；换别的主控就先运行 `scripts/make_fast_model.sh` |
  | B08 | 8 台，一次前向算 1/2/4/8 个 token 各要多久 | 多用户批处理、投机解码在 8 台上值不值得做？ |
  | B09 / B10 | 8 / 4 台，打开计时日志 | 每个 token 里计算和同步各占多少？（2 台时计算占约 90%） |
- **C：对网络延迟的敏感度**（约 30 分钟）。给每台 Pi 的网口加 1 ms 延迟后再测。
  - 需要 Pi 的 sudo 密码。所有 Pi 密码相同时这样写；不同时请告诉负责仓库的同学。
  - 每 token 的串行延迟次数 = (加延迟后的 ms/token − 不加时的 ms/token) ÷ 1 ms，可以和 RESULTS.md 里 Mac 模拟的数字比较。
  - 跑完会自动撤掉延迟。万一中途断了，手动撤掉：`PI_SUDO_PW=... scripts/exp/netem.sh 0`。

### 探索方向（单独跑一组用 `scripts/run_bench.sh`，参数说明见脚本开头）

```bash
NN=8 RPC_T=3 scripts/run_bench.sh tp                          # 8 台 TP，改进版，3 线程
NN=8 RPC_T=3 BUILD=stock scripts/run_bench.sh tp              # 同上，原版
NN=8 RPC_T=3 P=512 scripts/run_bench.sh tp                    # 长 prompt：看首 token 时间（prefill）
NN=8 RPC_T=3 ENV=GGML_RPC_NO_COMM=1 scripts/run_bench.sh tp   # 关掉 Pi 之间直接交换，全部经过主控
NN=4 RPC_T=3 EXTRA="-ts 1/1/1/0.8" scripts/run_bench.sh tp    # 不均匀切分（TP 下是否生效待验证）
NN=8 RPC_T=3 TRACE=1 scripts/run_bench.sh tp 1                # 记录每一步的耗时并自动分析，见 计时日志.md
NN=8 RPC_T=3 EXTRA="-p 1,2,4,8 -n 0" scripts/run_bench.sh tp 1   # 一次前向算 1/2/4/8 个 token 各要多久（判断投机解码、多用户批处理值不值）
```

可以考虑的问题：
1. `-t 3` 让 decode 快约 20%，但 prefill 慢约 22%。8 台时还是这样吗？
2. 2→4→8 台，改进版 TP 的速度曲线是什么样的？从第几台开始收益变小？
3. 更大的模型，比如 Qwen3-8B Q4_0（约 4.7 GB），一台装不下，只有集群能跑。需要先把模型放到主控上，再用 `MODEL=~/模型路径 scripts/run_bench.sh tp`。模型的 KV head 数要能被台数整除，否则会退回经过主控中转的慢路径。
4. PP 单个请求不快，但可能适合同时服务多个用户。可以用 `llama-server -np 4` 测同时处理多个请求时的吞吐。

### untied 模型（默认）和快速模型（可选）

- **untied 模型**（`~/exp/models/Llama-3.2-3B-Instruct-Q4_0-untied.gguf`，脚本默认用它）：原模型的输出层和输入词表共用一个矩阵，llama.cpp 的 TP 会让每台都完整算一遍输出层。untied 模型补了一个独立的 `output.weight`（内容一样），输出层就能按台数切分。**计算结果和原模型完全一样**（困惑度逐段相同），4 台 TP decode 从 2.99 提到 4.85 tok/s。`setup_pi.sh --model` 会在笔记本上自动生成并复制到主控（需要 `pip3 install numpy gguf`）。
- 想用原模型对比：命令前加 `MODEL='~/exp/models/Llama-3.2-3B-Instruct-Q4_0.gguf'`。
- **快速模型**（可选）：输出层从 Q6_K 改成 Q4_0，困惑度差 0.6%。原模型上 +9%，但 untied 以后输出层已经切开了，收益变小。需要时运行 `scripts/make_fast_model.sh`（rex 磁盘不够，已经从 rex 上删掉）。

## 第 9 步（需要时看）：Pi 型号不一样怎么办

- TP 把每一层平均分给所有 Pi，**大家都要等最慢的那台**。混进一台 Pi 4（1.5 GHz，Pi 400 是 1.8 GHz）或者降频的 Pi，整个集群就按它的速度走。体检表里有每台的型号和 CPU 频率。
- 核心验证（第 7 步）只用同型号的 Pi：在 `hosts.env` 里把它们排在前面，用 `NN=4` 或 `NN=8` 选；型号不一样的放到探索阶段，试试"不均匀切分"（上面最后一条命令），给慢的那台少分一点。
- **主控**一定要用内存 4 GB 以上的 Pi，它要读入整个模型。worker 只拿 1/N 的权重，内存小的也够。

## 常见问题

| 现象 | 原因和处理 |
|---|---|
| `rpc-server 启动失败` | 上一次的进程没退出，端口被占用。【在笔记本上】运行 `ssh 用户名@IP pkill -x ggml-rpc-server` |
| TP 卡在加载阶段不动 | 某两台 Pi 之间 51052 端口不通，或者某台的 rpc-server 挂了。先跑 `check_cluster.sh`；还不行就【在那台 Pi 上】看 `~/exp/logs/rpc.log` |
| 某一组结果显示"失败" | 看笔记本上 `logs/` 里对应的日志。原版多台时卡住超时属于预期 |
| 速度比预期慢很多 | 有 Pi 在降频（体检表里的 `!!`）、走的是 Wi-Fi，或者在跑别的程序 |
| `summarize.py` 的表里少了某一组 | 那一组中途被打断了。删掉 `logs/.done_<组名>` 后重跑 |
