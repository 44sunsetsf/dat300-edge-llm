# 计时日志：集群运行时每一步花了多少时间

改进版的 rpc-server 可以把**每条命令的耗时**记到一个 CSV 文件里。命令包括：计算一段子图、和其他 Pi 做 allreduce、接收输入、交出结果等。用这些日志可以把每个 token 的时间拆成"计算 / 同步 / 收发数据 / 空等"，也能看出哪台 Pi 拖慢了大家。

- 开关：启动 rpc-server 时设置环境变量 `GGML_RPC_TRACE=文件路径`。不设就完全不记录，对速度没有影响；开着时影响也很小（实测 2.93 → 2.90 tok/s）。
- 只有改进版（`~/llama.cpp/build/bin`，commit c1212b5 及以后）有这个功能，原版没有。

---

## 方法一：用脚本（最省事）—— 【在笔记本上】

```bash
NN=8 RPC_T=3 TRACE=1 scripts/run_bench.sh tp 1
```

跑完会自动做三件事：
1. 把每台 Pi 的日志取回到笔记本的 `logs/trace/<本次日志名>/`，每台一个文件，名字是 `用户名_IP.csv`；
2. 运行分析脚本，在终端打印每台 Pi 的时间拆分（见下面"怎么看分析结果"）；
3. 在同一个目录里生成 `segments.csv`（每个 token 的明细）和 `allreduce.csv`（每次同步的明细），方便自己用 Excel 或 pandas 分析。

可以和其他参数一起用，例如 `NN=4 TRACE=1 EXTRA="-p 512" scripts/run_bench.sh tp 1`。

## 方法二：手动

**1. 【在每台 Pi 上】启动 rpc-server 时加环境变量：**

```bash
cd ~/llama.cpp/build/bin
GGML_RPC_TRACE=$HOME/trace.csv ./ggml-rpc-server -H 0.0.0.0 -p 50052 -t 3 -c
```

**2. 【在主控 Pi 上】照常运行 llama-bench 或 llama-cli**（见 [`手动使用改进版.md`](手动使用改进版.md)）。

**3. 停掉 rpc-server（Ctrl+C），把日志取回笔记本 —— 【在笔记本上】：**

```bash
mkdir -p mytrace
scp cassian@<IP>:trace.csv mytrace/cassian.csv
scp rex@<IP>:trace.csv mytrace/rex.csv          # 每台 Pi 一个
python3 scripts/analyze_trace.py mytrace/*.csv
```

注意：每次启动 rpc-server 都会**覆盖**原来的 `trace.csv`。另外，日志会记下这个 rpc-server 运行期间的所有命令，包括加载模型和多次运行。所以想分析某一次运行，最好"启动 rpc-server → 只跑这一次 → 停掉"。

## 日志格式

每台 Pi 一个 CSV 文件，每行是这台 rpc-server 处理的一条命令：

| 列 | 意思 |
|---|---|
| `start_us` | 命令开始的时间（微秒，Unix 时间）。不同 Pi 的时钟不一定完全对齐，跨机器比较绝对时间时要小心 |
| `idle_us` | 处理这条命令之前空等了多久，也就是在等主控发下一条命令 |
| `dur_us` | 这条命令花了多久：接收数据 + 执行 + 回复 |
| `cmd` | 命令名，见下表 |
| `detail` | 附加信息，见下表 |

| 命令 | 是什么 | detail |
|---|---|---|
| `GRAPH_COMPUTE` / `GRAPH_RECOMPUTE` | 计算一段子图（几层里的一部分）。RECOMPUTE 是重复使用已经缓存的图 | `nodes=` 图里的算子数（只有 COMPUTE 有） |
| `COMM_ALLREDUCE` | 和其他 Pi 直接做 allreduce，即 TP 的同步。每个 token 56 次 | `bytes=` 每次交换的字节数；`steps=` 交换轮数（log2 台数）；`wait_compute_us=` 等自己这边的计算完成；`exchange_us=` 网络交换，**包括等对方 Pi 算完**；`local_us=` 本地拷贝 + 加法 |
| `SET_TENSOR` | 主控发来数据：每个 token 开头的输入，以及加载时的权重 | `bytes=` |
| `GET_TENSOR` | 主控取走结果，例如最后的 logits（513 KB） | `bytes=` |
| 其他 | 加载模型时的分配内存、初始化等，只在开头出现 | |

**一个 decode token 在每台 Pi 上的顺序：**

```
SET_TENSOR × 几个（输入）→ [GRAPH_RECOMPUTE → COMM_ALLREDUCE] × 56 → GRAPH_RECOMPUTE（最后一段）→（主控那台：GET_TENSOR 取 logits）
```

分析脚本就是按"计算或同步之后的第一个 SET_TENSOR"来切分 token 的。prefill 一次处理 32 个 token，所以那一段 allreduce 的字节数是 decode 的 32 倍，脚本靠这个区分 prefill 和 decode。

## 怎么看分析结果

示例：2 台 TP，改进版，rpc-server 3 线程。完整日志在 `logs/trace/example_tp_2n_opt_t3/`。

```
节点                     token数      总时间       计算       同步     其中网络     本地加     收发数据     空等主控     同步次数
cassian_192.168.31.30      31    353.8    315.9     26.0     21.7     3.2      1.4      6.8       56
rex_192.168.31.115         31    353.1    312.8     28.6     24.2     2.9      0.9      7.9       56
```

单位是 ms，表示平均每个 decode token。

- **总时间** ≈ 计算 + 同步 + 收发数据 + 空等主控。1000 ÷ 总时间 ≈ decode 速度：1000 ÷ 353 ≈ 2.8 tok/s。
- **计算占了约 90%**（313–316 ms），同步只占 7–8%。所以 2 台时，瓶颈已经主要是计算本身（内存带宽和线程数），不是网络。
- **同步里的"网络"包括等对方算完。** cassian 的网络时间比 rex 短，说明 rex 在等 cassian：cassian 是主控，同时还在跑 llama-bench，计算稍慢。哪台 Pi 的"网络"最短，哪台就是最慢的那台，大家都在等它。
- **空等主控**：rpc-server 没事做，在等主控采样、取 logits、发下一个 token 的输入。

## 可以自己分析的问题

- **8 台时，计算和同步各占多少？** 预测是计算降到约 40 ms（主控上 300 ms 的 1/8 左右），同步变成主要部分。对比 `NN=2/4/8 TRACE=1` 三次运行。
- **哪台 Pi 最慢？** 看 `allreduce.csv` 里同一个 `segment` 和 `index` 在各台的 `exchange_us`，最短的那台就是最慢的。可以和 `check_cluster.sh` 的温度、降频对照。
- **网络延迟到底多大？** 最快那台的 `exchange_us` 大致等于纯网络时间（它不用等别人）。8 台时每次 allreduce 有 3 轮（steps=3）。
- **线程数的影响**：`RPC_T=3` 和 `RPC_T=4` 各跑一次，看计算时间和同步时间怎么变。
- **prefill**：`segments.csv` 里 `ar_bytes` 大的那些段就是 prefill，可以单独分析。

`segments.csv` 的列：节点、段号、开始时间、总时间 `wall_us`、计算 `compute_us`（`n_compute` 段）、同步 `allreduce_us`（`n_allreduce` 次，每次 `ar_bytes` 字节；拆成 `ar_wait_compute_us` / `ar_exchange_us` / `ar_local_us`）、收发数据 `xfer_us`（`xfer_bytes` 字节）、空等 `idle_us`、其他 `other_us`。
