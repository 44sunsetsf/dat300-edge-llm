# 实验报告：扩展到 8 台设备（2026-10-21）

在上一次 4 台的基础上（[`实验报告_1014.md`](实验报告_1014.md)），这次用 7 台树莓派 + 1 块 LubanCat-5（RK3588）做了 8 台实验，并在**每台设备上采集 CPU / 内存 / 网络包**，用来给瓶颈做有依据的归因。英文正式报告见 [`../report/main.tex`](../report/main.tex)（图在 `report/figures/`）。

## 一、结论

| 4 / 8 台（TP，untied 模型） | prefill | decode (tok/s) |
|---|---|---|
| 单机 | 4.15 | 1.81–1.84 |
| 原版 llama.cpp，8 台 | 3.15 | 0.41 |
| 改进版，4 台 | 12.57 | 5.02 |
| 改进版，8 台（默认，主控线程忙等） | 13.39 | **1.62** |
| **改进版 + 关闭忙等（`GGML_RPC_NO_SPIN=1`），8 台** | **16.24** | **6.34** |
| PP，8 台（平均 / 给 cat 多分） | 4.06 / 4.98 | 2.00 / 2.29 |

**新发现的瓶颈（第 3 个）：8 台时主控的 CPU 被 RPC 分发线程的忙等占满。**
- 资源采集：8 台 decode 时主控 rex CPU 94%，其余 7 台只有 4–17%；
- 计时日志：每个 token 631 ms 里，**每台设备有约 470 ms 在空等主控**（4 台时只有 33 ms）；
- gdb 对主控进程采样：每台设备对应一个 `rpc_dispatcher` 线程，它们在命令不断时**忙等空转**（每个占 18–27% 的核）。8 台 = 8 个空转线程 + 主控自己 rpc-server 的 4 个计算线程，挤在 4 个核上，干活的线程抢不到 CPU。
- 优化：给 llama.cpp 加了开关 `GGML_RPC_NO_SPIN`（fork 的 commit `72578f5`），让分发线程阻塞等待。8 台 decode **1.62 → 6.34（3.9 倍）**，空等从 470 ms 降到 15 ms，worker CPU 从 15% 升到 61–65%。4 台 +6%（4.72 → 5.02），2 台不变。脚本现在默认打开这个开关。
- 排除的解释：主控 llama-bench 只用 1 线程、主控 rpc-server 少开线程 → 都没用（1.63）；让 cat 当主控（llama-bench 绑在 A55 小核）→ 4 台变快（5.31），8 台反而更慢（0.72），因为 8 个空转线程挤在更慢的小核上。

**资源采集给出的归因依据：**
- **单机受内存带宽限制**：单台 Pi CPU 99.7%，1.84 tok/s × 1.92 GB 权重 = 3.5 GB/s，是实测内存带宽（3.7–4.2 GB/s）的 70–85%；cat 12.28 tok/s = 23.6 GB/s，也是它的带宽上限。
- **网络不是瓶颈**：8 台时每台 worker 每 token 收发 3.9–4.3 MB、约 3200–3500 个包，最多 233 Mbit/s（链路实测 940 Mbit/s）。而且关闭忙等前后**网络量完全一样，速度差 3.9 倍**。每 token 字节数和公式 2×56×log₂N×12 KB 一致（2/4/8 台：1.4/2.8/4.1 MB，实测 1.7/2.8/3.9–4.3 MB）。
- **内存容量不是瓶颈**：8 台时每台 worker 的 rpc-server 只占约 260 MB。
- **PP**：每台只有 1/N 的时间在算（CPU 10–14%），网络几乎为零（每 token 30 kB，最后一台送 logits 513 kB）。

**其他：**
- 8 台时不均匀切分（`-ts`）会让直接同步退回主控中转（分片大小不一样），decode 只有 0.11。要支持异构加权，直接同步需要支持不等长分片（后续工作）。
- ag 同步算法在 8 台时也没用（1.56 vs 1.62，忙等开着时测的）。

## 补充：10 Mbps 限速下的 8 台对比（原版 vs 改进版 TP）

为了让 allreduce 改动的效果更明显，把 8 台设备的网卡都限到 10 Mbps（`ethtool advertise 0x002`，交换机端口随之以 10 Mbps 运行；Mac 的端口保持千兆）。10 Mbps 下加载权重每次要 8 分钟以上（TP 的小分片不会被 rpc-server 缓存），所以 `scripts/exp/bw_limit.sh` 在模型加载完、主控开始预热生成时才切到 10 Mbps，测完自动恢复千兆。只测 decode，开着资源采集。

| 8 台 TP（untied） | 链路 | decode (tok/s) | 主控每 token 流量 | worker 每 token 流量 |
|---|---|---|---|---|
| 原版 | 1 Gbit/s | 0.41 | — | — |
| 改进版（直接 allreduce + 关闭忙等） | 1 Gbit/s | 6.34（15 倍） | 5.0 MB | 3.9 MB |
| 原版 | 10 Mbit/s | **0.01** | **200.7 MB** | 28.6 MB |
| 改进版 | 10 Mbit/s | **0.20–0.26（20–26 倍）** | **5.3 MB** | 4.4 MB |

- 原版把所有部分和经过主控中转：主控每 token 收发约 200 MB，上行跑满（8.9 Mbit/s），一个 token 约 100 秒。
- 改进版主控每 token 只有 5.3 MB（少约 40 倍），每台 worker 4.4 MB，和公式一致。两次测量分别是 0.20 和 0.26 tok/s，比原版快 20–26 倍，比千兆下的 15 倍更明显。
- 10 Mbps 下改进版也受网络限制：每 token 有 56×3 = 168 轮串行交换，每轮光是把 12 KB 发出去就要约 10 ms。
- 交换机被重置后的密码提示不接受自动输入，所以没在交换机上设端口速率，改在设备网卡上限速，效果等同（端口速率由两端协商）。

## 二、设备性能指标（实测）

| 设备 | SoC / CPU | 内存带宽（4 线程，单线程） | 到主控 RTT | 单机 prefill / decode |
|---|---|---|---|---|
| Pi 400 ×4（rex 主控、finn、han、cassian） | BCM2711，4×A72 1.8 GHz，4 GB LPDDR4 | 3.7–4.2 GB/s（5.3） | 0.06–0.09 ms | 4.15 / 1.84 tok/s |
| Pi 4B ×3（luthen、jarjar、crosshair） | 同上 | 4.0–4.2 GB/s（5.3） | 0.07–0.09 ms | 同 SoC |
| LubanCat-5（cat） | RK3588，4×A76 2.3 GHz + 4×A55，4 GB | 21–23 GB/s（21.6） | 0.24 ms | 48.75 / 12.28 tok/s |

网络：全部千兆，两台之间 TCP 实测 940 Mbit/s。内存带宽用 `tools/membw.c`（STREAM 风格 copy/triad），TCP 用一个 Python 单连接测速。

## 三、资源采集怎么做的

- `tools/mon.c`（静态编译成 `tools/mon-arm64`，Pi 和 RK3588 都能直接跑）：每 0.5 秒读 `/proc/stat`、`/proc/meminfo`、rpc-server / llama-bench 的常驻内存、网卡字节数和包数、温度。`run_bench.sh` 默认在每台设备上启动（`MON=0` 关闭），结果在 `logs/mon/<日志名>/`。
- 主控上 llama-bench 加 `--progress` 并给每行打时间戳，`scripts/analyze_mon.py` 据此只统计 prefill 和 decode 两段（排除加载模型时上传权重的流量和预热）。
- Pi 没有电池时钟、不能上网，时间会漂、重启会乱：每次采集前测每台设备和笔记本的时钟差（实测 0.4–1.5 秒），分析时修正。
- 开销：最初的 shell 版本每次采样要起好几个进程，让 decode 慢了 5%；换成 C 版本后 2 台测不出差别（3.43–3.44 vs 3.44），4 台满载时约 2–3%（4.72–4.75 vs 4.85）。

## 四、过程中的问题

- 交换机这周被重置过，DHCP 配置没了；上周设了固定 IP 的 5 台不受影响，新加的 3 台（cassian、jarjar、crosshair）我同样设成固定 IP（.7/.8/.9）。
- **jarjar 供电不足**：8 台测试中途欠压重启了一次（内核日志 `Undervoltage detected`，降频标志 0x50000），换电源后正常。
- 为节省时间砍掉了几项次要测试（8 台 PP 长 prompt 流水线、8 台多请求吞吐、给 cat 分 4 份的 TP），8 台给 cat 分 2 份的 TP 已经说明问题。

## 五、复现

```bash
scripts/setup_pi.sh --model            # 8 台安装（hosts.env 顺序见 scripts/exp/study_1021.sh 开头）
scripts/exp/study_1021.sh all          # 本报告的实验（S：扩展性，T：对照，P：PP，B：多请求）
NN=8 RPC_T=4 TRACE=1 scripts/run_bench.sh tp 1      # 8 台 TP + 计时日志 + 资源采集
python3 scripts/analyze_mon.py logs/mon/<日志名>      # 重新分析某次的资源采集
python3 report/make_figures.py                      # 重新生成报告里的图
```

原始数据：`logs/*_1021_*.log`（RESULT 行）、`logs/mon/*_1021_*/`（每台设备的采集 CSV、阶段时间戳、汇总 `mon_summary.csv`）、`logs/trace/*_1021_*/`（计时日志）。主要测试编号：S01–S05、T01–T05、P01–P04、D1–D6（主控瓶颈诊断）、F1–F3（关闭忙等）。
